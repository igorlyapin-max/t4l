КОНЦЕПЦИЯ ПРИЛОЖЕНИЯ ДЛЯ УЧЕТА И ПЛАНИРОВАНИЯ ВРЕМЕНИ по мотивам идей
учета времени из «Этой странной жизни»

Примечание Это современная интерпретация системы учета времени.
Приложение не должно сводиться только к задачам: оно описывает жизнь как
непрерывный набор таймлайнов, а задачи являются лишь одним из способов
классификации времени.

1.  ОСНОВНАЯ ИДЕЯ

Приложение должно отвечать на несколько разных вопросов:

-   На что ушло мое время?
-   Чем я занимался?
-   Над какой задачей или проектом работал?
-   Где я находился?
-   Что было запланировано и что получилось фактически?
-   Насколько точно я умею оценивать длительность задач?
-   Как распределяется моя жизнь между работой, сном, дорогой, отдыхом,
    семьей, обучением и другими областями?

Ключевой принцип:

Время существует непрерывно, а задачи, деятельность, местоположение и
другие характеристики являются классификаторами этого времени.

2.  УЧЕТ ЧЕРЕЗ МГНОВЕННЫЕ СОБЫТИЯ

Вместо хранения готовых интервалов:

Начало: 10:00 Конец: 11:30 Категория: Работа

система хранит события переключения состояния:

08:00 Сон 08:25 Быт 09:10 Дорога 09:45 Работа 12:30 Обед 13:10 Работа

Событие содержит только момент изменения состояния.

Базовая структура:

Event - timestamp - timeline_id - category_id - дополнительные
метаданные при необходимости

У события нет обязательного end_time.

Конец интервала определяется временем следующего события в том же
таймлайне.

Например:

09:45 Работа 12:30 Обед

означает:

Работа = [09:45, 12:30)

Преимущества:

-   естественная непрерывность учета;
-   меньше дублирования данных;
-   не требуется синхронизировать start/end соседних интервалов;
-   легко вставлять пропущенное переключение задним числом;
-   история становится журналом событий;
-   интервалы и статистика могут вычисляться из событий.

3.  ПОНЯТИЕ «ТАЙМЛАЙН»

Вместо термина dimension используется термин «таймлайн».

Таймлайн — независимый поток классификации времени.

Каждый таймлайн отвечает на свой вопрос.

Примеры:

Таймлайн «Деятельность» Что я делал?

Таймлайн «Задачи» Над чем я работал?

Таймлайн «Местоположение» Где я находился?

Таймлайн «Контекст» В каком режиме или окружении происходила
деятельность?

Каждый таймлайн имеет собственные события переключения.

Изменение категории в одном таймлайне не должно автоматически завершать
категории в других таймлайнах.

4.  ПАРАЛЛЕЛЬНЫЕ ТАЙМЛАЙНЫ

В один физический момент времени могут одновременно действовать разные
классификации.

Например, в 14:00:

Деятельность: Работа → Разработка

Задачи: Проект X → Backend → API

Местоположение: Офис

Контекст: Компьютер

Это не означает четыре часа учета за один час.

Это четыре разных описания одного и того же физического времени.

Таким образом, приложение может отвечать на запросы:

-   сколько времени я работал;
-   сколько времени потратил на Project X;
-   сколько времени работал дома;
-   сколько времени программировал в офисе;
-   сколько времени читал в дороге;
-   сколько рабочего времени ушло на конкретный проект.

5.  ДРЕВОВИДНЫЕ КЛАССИФИКАТОРЫ

Категории внутри таймлайна образуют дерево.

Пример таймлайна «Деятельность»:

Жизнь ├── Сон ├── Работа │ ├── Разработка │ │ ├── Проектирование │ │ ├──
Программирование │ │ ├── Отладка │ │ └── Code Review │ ├── Совещания │
└── Административная работа ├── Отдых │ ├── Чтение │ │ ├──
Художественная литература │ │ └── Профессиональная литература │ ├── Кино
│ └── Игры ├── Быт │ ├── Уборка │ ├── Готовка │ └── Покупки ├── Дорога
└── Спорт

Это позволяет анализировать данные на разной глубине.

Например:

Работа — 147 часов

или:

Работа — 147 часов Разработка — 92 часа Программирование — 61 час
Отладка — 18 часов Проектирование — 13 часов Совещания — 31 час
Административная работа — 24 часа

6.  НЕСКОЛЬКО ДЕРЕВЬЕВ

Каждый таймлайн имеет собственное дерево категорий.

Пример 1. Деятельность

Работа Отдых Сон Быт Дорога Спорт

Пример 2. Задачи

Рабочие проекты ├── Project X │ ├── Backend │ │ ├── API │ │ └── Database
│ └── Frontend └── Project Y

Личные проекты ├── Изучение английского └── Дом

Пример 3. Местоположение

Дом ├── Кабинет └── Прочее

Работа ├── Офис └── Клиент

Дорога ├── Автомобиль ├── Пешком └── Общественный транспорт

Пример 4. Контекст

Компьютер Телефон Офлайн Общение

7.  ЗАДАЧИ КАК ОДИН ИЗ ТАЙМЛАЙНОВ

Задача не должна быть единственной основой учета времени.

Можно заниматься деятельностью без конкретной задачи:

Сон Дорога Обед Отдых Уборка Чтение

Поэтому таймлайн «Задачи» может быть независимым и при необходимости
иметь специальное состояние:

Нет задачи

Например:

Деятельность: 14:00 Работа → Разработка

Задача: 14:00 Project X → API

Местоположение: 13:30 Офис

В 15:20 пользователь закончил API, но продолжил работать:

Задача: 15:20 Нет задачи

При этом таймлайн «Деятельность» остается в категории «Работа →
Разработка», пока пользователь явно его не переключит.

8.  ПЕРЕСЕЧЕНИЕ ТАЙМЛАЙНОВ

Особенно ценная аналитика возникает при пересечении таймлайнов.

Примеры:

Деятельность = Работа И Местоположение = Дом

Результат: Сколько времени я работал дома?

Деятельность = Чтение И Местоположение = Дорога

Результат: Сколько времени я читал в дороге?

Задача = Project X И Деятельность = Разработка

Результат: Сколько времени Project X потребовал именно программирования?

Задача = Project X И Местоположение = Офис

Результат: Сколько времени над Project X я работал в офисе?

Архитектура должна позволять вычислять пересечения интервалов разных
таймлайнов.

9.  НЕПРЕРЫВНОСТЬ И НЕИЗВЕСТНОЕ СОСТОЯНИЕ

Нужно отдельно определить правила начала и конца данных.

Например, если последнее событие:

22:45 Сон

то оно теоретически действует до следующего события.

Однако нельзя автоматически считать, что состояние продолжается
бесконечно.

Для отчетов интервал последнего события можно ограничивать: - текущим
моментом; - концом анализируемого дня; - следующим событием; -
специальным состоянием «Неизвестно».

Стоит предусмотреть категорию:

Не классифицировано / Неизвестно

Это позволит видеть пробелы учета, а не скрывать их.

10. ПАРАЛЛЕЛЬНЫЕ АКТИВНОСТИ ВНУТРИ ОДНОГО ВРЕМЕНИ

Отдельно от параллельных таймлайнов существует реальное совмещение
деятельности.

Например:

18:00–19:00 — прогулка. 18:00–19:00 — аудиокнига.

Физически прошел один час, но он имеет несколько смысловых
характеристик.

Можно использовать понятия:

Primary activity — основная активность. Secondary activity — вторичная
активность.

Например:

Primary: Прогулка — 60 минут.

Secondary: Аудиокнига — 60 минут.

При этом Total physical time = 60 минут, а не 120.

Для этого можно либо создать отдельный таймлайн вторичной деятельности,
либо предусмотреть тип/роль таймлайна.

11. ТИПЫ НАГРУЗКИ

Для планирования полезно классифицировать деятельность по требуемому
вниманию.

Focus Практически полное внимание: - программирование; - написание
текста; - сложное чтение.

Light Небольшая когнитивная нагрузка: - почта; - организационные задачи.

Background Процесс идет практически без участия человека: -
компиляция; - загрузка; - автоматический расчет.

Compatible Деятельность допускает осмысленное совмещение: - прогулка +
аудиокнига; - дорога пассажиром + чтение.

Это позволит определять допустимость параллельного учета.

12. ПЛАНИРОВАНИЕ

Учет фактического времени и планирование логически следует разделить, но
система должна поддерживать два взаимодополняющих способа планирования:

1.  Бюджетирование времени.
2.  Планирование непосредственно на временной шкале.

Фактический учет хранится через события таймлайнов.

Бюджетирование отвечает на вопрос: «Сколько времени я хочу или могу
выделить на определенную деятельность, категорию или задачу?»

Планирование на временной шкале отвечает на другой вопрос: «Когда именно
у меня есть время и чем я собираюсь заниматься в конкретный промежуток?»

Это особенно важно при жестком расписании.

Например:

08:00–09:00 Дорога 09:00–12:00 Работа 12:00–13:00 Обед 13:00–15:30
Работа 15:30–16:15 Свободное окно 16:15–18:00 Работа 18:00–19:00 Дорога

В данном случае недостаточно знать, что за день имеется 45 минут
свободного времени. Существенно знать, что это конкретное непрерывное
окно 15:30–16:15.

Это позволяет выбирать задачи не только по суммарному дневному бюджету,
но и по размеру доступного временного окна.

Например:

Задача A — 20 мин Задача B — 40 мин Задача C — 1 ч 30 мин

В окно 15:30–16:15 можно поместить задачу B либо задачу A вместе с
другой короткой задачей, но нельзя целиком поместить задачу C.

Таким образом, планировщик должен работать одновременно:

-   с суммарной емкостью дня;
-   с конкретными занятыми интервалами;
-   со свободными окнами между ними;
-   с длительностью задач;
-   с возможностью или невозможностью дробления задачи.

Планирование на временной шкале концептуально должно использовать ту же
временную модель, что и фактический учет, но плановые и фактические
данные необходимо различать.

Возможные варианты реализации:

-   отдельные плановые таймлайны;
-   признак planned / actual;
-   отдельный слой PlannedEvent / PlannedInterval поверх общей модели
    таймлайнов.

Конкретный вариант следует определить при проектировании модели данных.

Важно поддерживать сравнение не только суммарного времени, но и
расписания.

Например:

План: 15:30–16:10 — Задача B

Факт: 15:37–16:22 — Задача B

Это позволит анализировать точность соблюдения расписания.

У задачи могут быть поля:

-   estimate — первоначальная оценка;
-   remaining_estimate — оставшаяся оценка;
-   budget — допустимый бюджет времени;
-   deadline — срок;
-   value — ценность;
-   energy — требуемый уровень концентрации;
-   progress — прогресс;
-   project/category — положение в дереве задач.

В дальнейшем автоматический планировщик сможет учитывать одновременно:

-   доступный бюджет дня;
-   конкретные свободные окна;
-   ожидаемую длительность задачи;
-   возможность дробления задачи;
-   дедлайн;
-   ценность/приоритет;
-   требуемый уровень энергии;
-   ограничения расписания.

13. БЮДЖЕТ ВРЕМЕНИ

Пример:

Сегодня доступно: 6 ч 20 мин Зарезервировано: 2 ч 10 мин Свободно: 4 ч
10 мин

Не следует планировать 100% доступного времени.

Планируемая емкость:

available_time × load_factor

Например:

6 часов × 0.75 = 4 часа 30 минут планируемой активной работы.

14. РАСПРЕДЕЛЕНИЕ БОЛЬШОЙ ЗАДАЧИ

Например:

Написать прототип API Оценка: 6 часов Срок: пятница

Приложение может предложить:

Пн — 1:30 Вт — 1:30 Ср — 1:30 Чт — 1:30 Пт — резерв

Таким образом задача планируется относительно доступного бюджета
времени.

15. ОБУЧЕНИЕ НА ФАКТИЧЕСКОЙ СТАТИСТИКЕ

Необходимо сохранять первоначальную оценку задачи.

Например, пользователь регулярно оценивает задачи в 1 час, а фактически
получает:

1:47 1:32 2:05 1:41

Можно вычислять персональный коэффициент:

planning_factor = median(actual / estimate)

Например:

planning_factor = 1.7

При следующей оценке в 2 часа приложение может показать:

Пользовательская оценка: 2:00 Прогноз по предыдущей статистике похожих
задач: примерно 3:25

Первоначальная оценка не изменяется, чтобы можно было анализировать
развитие навыка планирования.

Цикл:

оценил → запланировал → сделал → измерил → сравнил → скорректировал
будущий прогноз.

16. АНАЛИТИКА «НА ЧТО УШЛА МОЯ ЖИЗНЬ»

Пример месячного отчета:

Сентябрь — 720 часов

Сон — 231 ч Работа — 147 ч Семья — 72 ч Быт — 41 ч Дорога — 29 ч
Обучение — 24 ч Спорт — 17 ч Развлечения — 46 ч Не классифицировано —
113 ч

При раскрытии категории:

Работа — 147 ч Разработка — 92 ч Совещания — 31 ч Административная
работа — 24 ч

Можно сравнивать план и факт:

Обучение План: 30 ч Факт: 17 ч 40 мин

17. ВАЖНОЕ РАЗЛИЧИЕ МЕТРИК

Нельзя бездумно складывать длительности разных таймлайнов.

Например, один час может одновременно быть:

Деятельность = Работа Задача = Project X Место = Офис

Это по-прежнему один физический час.

Поэтому аналитика должна различать:

Physical / elapsed time Фактически прошедшее время.

Classified time Сколько физического времени получило определенную
классификацию в конкретном таймлайне.

Cross-timeline time Продолжительность пересечения нескольких условий.

Secondary/parallel activity time Дополнительная характеристика того же
физического времени.

18. ПРЕДЛАГАЕМАЯ МОДЕЛЬ ДАННЫХ

Timeline - id - name - type - settings - is_active

Category - id - timeline_id - parent_category_id - name - sort_order -
archived

Event - id - timeline_id - category_id - timestamp - source - note -
created_at - updated_at

Task - id - category_id или связь с деревом задач - title - estimate -
remaining_estimate - budget - deadline - value - energy - progress -
status

DailyPlan - date - available_time - load_factor

PlannedTask - daily_plan_id - task_id - planned_duration - planned_start
(опционально) - priority/order

Важно: Интервалы фактического учета не обязательно хранить как первичные
данные. Их можно вычислять из Event.

19. ПРОИЗВОДНЫЙ ИНТЕРВАЛ

Из:

Event A: 10:00, timeline=Activity, category=Work

Event B: 12:30, timeline=Activity, category=Lunch

получается производный интервал:

timeline = Activity category = Work start = 10:00 end = 12:30 duration =
2:30

Для производительности такие интервалы впоследствии можно кэшировать или
материализовать, но источником истины остается журнал событий.

20. РЕДАКТИРОВАНИЕ ПРОШЛОГО

Event-based подход особенно удобен для исправлений.

Было:

09:00 Работа 12:00 Обед

Пользователь вспомнил, что с 10:30 до 11:00 был в дороге.

Добавляется:

10:30 Дорога 11:00 Работа

После пересчета:

09:00–10:30 Работа 10:30–11:00 Дорога 11:00–12:00 Работа

Не требуется вручную изменять end_time соседних записей.

21. MVP

Таймлайн является универсальным классом сущностей, а не заранее заданным
набором.

Приложение не должно требовать наличия конкретных таймлайнов вроде
«Деятельность», «Задачи» или «Местоположение».

Пользователь сам определяет:

-   сколько таймлайнов ему нужно;
-   как они называются;
-   какую информацию они описывают;
-   какие деревья категорий используются внутри;
-   какие таймлайны участвуют в учете, планировании и аналитике.

Например, один пользователь может создать:

Деятельность Проекты

Другой:

Работа Местоположение Настроение Уровень энергии

Третий может использовать всего один таймлайн.

Таймлайн «Настроение» может, например, иметь дерево:

Настроение ├── Позитивное │ ├── Спокойное │ └── Воодушевленное ├──
Нейтральное └── Негативное ├── Усталость ├── Раздражение └── Тревога

Это позволяет анализировать пересечения произвольных пользовательских
таймлайнов.

Например:

Деятельность = Работа И Настроение = Воодушевленное

или:

Проект = Project X И Настроение = Усталость

Готовые таймлайны следует рассматривать только как необязательные
шаблоны быстрого старта, а не как фиксированную модель приложения.

Примеры шаблонов:

«Деятельность» Сон, работа, дорога, отдых, быт, спорт.

«Задачи / проекты» Рабочие и личные проекты с вложенной структурой.

«Местоположение» Дом, офис, дорога и пользовательские места.

«Настроение» Пользовательское дерево состояний.

«Энергия» Высокая, средняя, низкая.

Пользователь должен иметь возможность:

-   создать таймлайн с нуля;
-   создать таймлайн из шаблона;
-   самостоятельно назвать его;
-   полностью изменить дерево категорий;
-   архивировать таймлайн;
-   отказаться от любого предложенного шаблона;
-   создавать произвольное количество собственных таймлайнов в рамках
    технических ограничений системы.

Первая версия MVP:

1.  Универсальная сущность Timeline.
2.  Создание произвольных пользовательских таймлайнов.
3.  Создание таймлайна с нуля.
4.  Необязательные шаблоны быстрого старта.
5.  Древовидные категории каждого таймлайна.
6.  Добавление мгновенного события переключения категории.
7.  Автоматическое построение интервалов из событий.
8.  Редактирование истории событий.
9.  Отчеты день / неделя / месяц.
10. Агрегация по любому уровню дерева.
11. Пересечение двух или нескольких произвольных таймлайнов.
12. Задачи с оценкой времени.
13. Бюджетирование доступного времени.
14. Планирование на временной шкале с учетом конкретных свободных окон.
15. План/факт как по суммарной длительности, так и по расписанию.
16. Коэффициент ошибки планирования.

На первом этапе можно не добавлять:

-   AI;
-   сложные интеграции;
-   Pomodoro;
-   привычки;
-   большое количество визуализаций.

22. СЛЕДУЮЩИЙ ЭТАП ПРОЕКТИРОВАНИЯ

После фиксации концепции стоит подробно спроектировать:

1.  SQL-схему Timeline / Category / Event / Task.
2.  Универсальную модель пользовательских таймлайнов и необязательных
    шаблонов.
3.  Правила непрерывности таймлайнов.
4.  Алгоритм преобразования Event → Interval.
5.  Алгоритм пересечения произвольных таймлайнов.
6.  Правила Primary / Secondary активности.
7.  Модель плановых и фактических данных: planned / actual.
8.  Представление жестко занятых и свободных временных окон.
9.  Алгоритм подбора задач под конкретные свободные окна.
10. Обработку часовых поясов и переходов времени.
11. Редактирование и удаление событий.
12. Кэширование производных интервалов.
13. API для записи мгновенного события.
14. Алгоритм автоматического планирования задач на день.
